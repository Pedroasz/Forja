# V4.3A.1 current professional system audit

Date: 2026-07-25

Base: `42fe96043e51df0e8d12fcc333fb383b46550b33` (`origin/main`)

Scope: read-only audit for the professional consultation design

## Executive summary

FORJA already has the identity, relationship, workspace and server-authoritative authorization foundation needed to add consultations incrementally. It does not yet have consultation records. The current “Consultas” screen is explicitly a visual placeholder and writes no data.

The safest compatible path is to:

1. keep `professional_student_relationships` as the v1 link authority;
2. add an explicit consultation capability and consultation-specific RPC boundary;
3. use a relational consultation aggregate with immutable finalized snapshots;
4. keep professional-private data private by default and publish only explicit versions;
5. keep sensitive consultation drafts server-authoritative rather than adding them to the current generic browser cache or sync queue;
6. integrate a small consultation controller into the existing monolithic `index.html` only after the database boundary is tested.

No application, database, Supabase remote, Storage or production state was changed by this audit.

## Current professional identity and workspace model

### Account identity

The current commercial account foundation separates:

- primary account type: `individual`, `trainer` or `nutritionist`;
- account modes: `individual`, `student`, `trainer` and `nutritionist`;
- active workspace: a presentation and capability context;
- professional relationships: the authority to reach another user’s data.

This separation is valuable. A visible nutritionist or trainer workspace is not evidence that a client relationship exists. Likewise, an organization membership is not sufficient to read a consultation.

Compatibility constraint: the current primary professional type is scalar. V4.3 must persist the author’s professional type on each consultation and validate it against the authoritative commercial account at creation. Supporting one person acting simultaneously as trainer and nutritionist would require a separate product and identity decision.

### Workspace bootstrap

Authenticated workspace resolution loads authoritative access context before exposing role-specific screens. This avoids treating local role flags as authorization. Consultation routes should remain unavailable when the authoritative relationship or capability load is uncertain.

### Navigation

The nutritionist workspace currently exposes:

- Pacientes;
- Consultas;
- Dietas;
- Evolução;
- Perfil.

The trainer workspace currently exposes:

- Alunos;
- Treinos;
- Evolução;
- Feedbacks;
- Perfil.

The consultation route is a placeholder. The V4.3A.2I frontend checkpoint should introduce the same consultation entry point for both professions without disturbing Diet, Treino or Evolução.

## Current relationship and authorization model

`professional_student_relationships` is the v1 client-link authority. Relevant fields and constraints include:

- `professional_user_id` and `student_user_id`;
- `professional_type` constrained to `trainer` or `nutritionist`;
- optional `organization_id`;
- lifecycle status including `active`;
- a constrained JSON scope object;
- unique independent and organization-context relationships;
- participant-scoped reads plus an existing organization-admin metadata path.

Existing scopes cover workout, nutrition and evolution operations. None authorize consultations. Reusing a broad existing scope would conflate unrelated privileges. A later migration should add a consultation-specific capability, such as `manage_consultations`, and define any cross-professional shared-history capability separately.

The current relationship SELECT policy lets organization owners and admins see relationship rows. That pattern must not automatically extend to consultation content. Organization administrators may need operational metadata in the future, but clinical-style content remains inaccessible unless a separate, explicit product policy is approved.

The current default-scope trigger runs on both insert and update and replaces the scope object with profession defaults. Adding consultation scopes only to the JSON constraint would therefore be unsafe: a later relationship update could erase an explicitly selected value. A.2B must update the constraint, existing rows, default helper and trigger atomically, changing the helper to fill missing defaults without overwriting explicit choices.

The repository has a complete trainer invite/accept flow, but no equivalent self-service nutritionist-patient invitation flow was found. The consultation design can authorize both professions once an active generic relationship exists; it must not claim that a nutritionist can currently create that relationship through the product UI.

### Reusable RLS and RPC conventions

The current repository already demonstrates:

- RLS on exposed tables;
- narrow `authenticated` grants and broader `service_role` maintenance grants;
- `security definer` functions with an empty `search_path`;
- server-side professional identity checks;
- active-relationship and scope checks;
- immutable assignment snapshot protection;
- indexed relationship lookups;
- RPC-based writes for high-risk transitions.

V4.3 should preserve these conventions and tighten them for more sensitive data:

- deny by default;
- no `anon` access;
- no direct draft table writes from the browser;
- explicit `auth.uid()` checks inside definer functions;
- content reads through bounded RPCs or views with RLS-safe semantics;
- no policy based on user-editable JWT metadata;
- indexes for every relationship, author, subject, publication and lease predicate used by RLS.

## Current professional plans and immutable records

Workout and nutrition workflows separate editable templates from immutable assigned snapshots. Assignment versions preserve the title and plan payload at the time of assignment, while later status changes do not rewrite the snapshot.

This is the closest existing pattern for finalized consultations. A consultation needs stronger boundaries:

- the draft remains relational and editable only by the author;
- finalization creates an immutable canonical snapshot and hash;
- published client content is a separate immutable manifest, not an alias for the author’s live record;
- addenda append corrections without rewriting the finalized snapshot;
- visibility grants can change only through audited operations and never mutate historical content.

## Notifications

The notification foundation supports relationship, workout, nutrition and system events. It:

- scopes reads to the recipient;
- uses controlled database creation;
- limits frontend metadata and routes;
- uses user-scoped caching and polling.

Consultation notifications are not yet modeled. When later introduced:

- use a consultation-safe event type and route allowlist;
- include identifiers and neutral status text only;
- never include anamnesis, measurements, comments, attachment names or formula results in notification payloads;
- deduplicate reminders and attendance confirmations;
- keep external WhatsApp, email and push delivery out of v1.

## Browser storage and offline behavior

The existing `StorageService` and `SyncQueue` are designed around personal module snapshots such as meals, hydration, evolution and workouts. They are user-scoped, but they are not a consultation operation log, do not implement field-level sharing, and do not provide an editing lease.

Adding consultation payloads to that queue would create material risks:

- sensitive content could persist in browser storage;
- last-write-wins behavior could overwrite another device;
- finalization or publication could race with queued drafts;
- logout and account switching would require new erasure guarantees;
- attachment and snapshot consistency would be difficult to prove.

V4.3 v1 should therefore be online-first and server-authoritative. A draft can remain in memory while a request is pending, but must show explicit saved, unsaved, reconnecting and conflict states. Durable offline consultation storage is a separate security design.

## Current Storage conventions

The current application contains no consultation attachment bucket or attachment authorization model. Supabase Storage access must therefore be designed from first principles in A.2H:

- private bucket only;
- random object identifier, not a guessable filename;
- database metadata as the authorization source;
- explicit per-attachment publication;
- short-lived signed access returned only after database authorization;
- MIME, size, extension and content validation;
- checksum and immutable finalized association;
- no public URLs and no sensitive metadata in the object path.

No bucket or Storage policy is created in V4.3A.1.

## Compatibility risks

| Risk | Why it matters | Design response |
| --- | --- | --- |
| UI capability treated as authority | Browser state can be stale or manipulated. | Enforce identity, active link, profession, ownership and state in RPCs/RLS. |
| Organization role leaks content | Existing relationship metadata is visible to some admins. | Never inherit that policy for consultation content; keep admin access metadata-only unless explicitly approved. |
| Existing scope reused too broadly | Workout or nutrition scopes do not express consultation consent. | Add narrow consultation scopes and test every actor matrix cell. |
| Generic sync queue extended | It lacks lease, conflict and immutable-finalization semantics. | Use server-authoritative drafts and optimistic revision checks. |
| Client sees the author record directly | Private fields or later edits could leak. | Publish an immutable allowlisted manifest and read only that manifest. |
| Finalization implemented as a status flip | Relational child rows could still drift. | Build and hash a canonical immutable snapshot inside the finalization transaction. |
| Cross-professional history is over-broad | “Common” can be misread as all content. | Share only common fields explicitly classified and individually granted. |
| Formula inputs inferred from identity | Identity and source-required physiology are different concepts. | Store identity separately; request an explicit physiological reference parameter with provenance. |
| Monolithic frontend grows without seams | `index.html` is already large and regression-prone. | Add a small namespace/controller, narrow DOM island and dedicated tests in A.2I. |
| Windows line endings affect a legacy test | The current role-workspace test includes a repository-wide LF assertion and reports 37/38 on a clean Windows checkout with system `core.autocrlf=true`. | Treat as a pre-existing baseline limitation; do not alter application files in this documentation branch. |

## Reusable implementation patterns

1. Active relationship checks from the role-based workspace hardening functions.
2. Professional-type assertions before mutation.
3. Server-generated immutable plan snapshots and monotonically increasing versions.
4. Partial unique indexes for one active assignment; adapt the idea to one live lease per consultation.
5. User-scoped, route-allowlisted notifications with content-minimal payloads.
6. Online-only professional monitoring with date ranges, pagination and safe text rendering.
7. Database-generated writes for relationship and assignment transitions.
8. `PermissionService` as a presentation gate backed by database authority.
9. Professional monitoring RPCs that accept `relationship_id`, derive the client server-side, validate organization context, and return bounded keyset-paginated DTOs.
