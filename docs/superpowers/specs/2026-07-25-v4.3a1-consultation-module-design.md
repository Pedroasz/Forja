# V4.3A.1 professional consultation module design

Status: proposed architecture for approved V4.3 product decisions

Date: 2026-07-25

Application base: `42fe96043e51df0e8d12fcc333fb383b46550b33`

Implementation begins only in V4.3A.2

## Purpose

Design the first FORJA “Start Consultation” module for trainers and nutritionists without turning FORJA into a general medical-record system.

The module is for manual, adult professional consultations with already linked FORJA clients. It supports a common assessment core, profession-specific private content, repeated measurements, curated calculations, controlled sharing, explicit client publication, attachments and immutable history.

This document defines boundaries and contracts. It does not create migrations, schema, UI, formulas, buckets, PDFs, notifications or remote resources.

Related documents:

- [Current professional system audit](../../audits/v4.3a1-current-professional-system-audit.md)

## Design principles

1. **Author + subject is the security domain.** Organization is provenance and billing context, not a right to consultation content.
2. **Server authority before UI.** Account type, active relationship, scope, ownership, lifecycle and publication are enforced in PostgreSQL/RPCs.
3. **Private by default.** Profession-specific content, attachments and PDFs are private until an explicit share or publication exists.
4. **Immutable meaning.** Finalization captures exactly what the professional finalized; later corrections append an addendum or become a new reassessment.
5. **No hidden inference.** Calculations expose method, version, inputs, physiological branch, limits and overrides.
6. **Identity is not a coefficient.** Gender identity is never silently converted into a formula’s source-required physiological parameter.
7. **Online-first sensitive drafts.** No consultation draft is persisted in `localStorage` or the current generic sync queue.
8. **Progressive disclosure.** The client sees only a published manifest; another professional sees only authorized common or individually shared items.
9. **Plain records, not diagnosis.** Warnings and reference bands assist review but do not diagnose.
10. **YAGNI.** No generalized EHR, billing engine, legal signature, device integration or external messaging platform.

## Actors and invariants

### Actors

- **Author professional:** authenticated trainer or nutritionist who created the consultation.
- **Subject/client:** adult FORJA account linked to the author in v1.
- **Other linked professional:** a different authenticated professional with an active relationship to the same subject.
- **Organization owner/admin:** manages organization metadata but receives no consultation-content privilege from that role.
- **Maintenance service:** trusted backend operation, never a browser credential.
- **Anonymous or unrelated authenticated user:** has no access.

### Invariants

- `author_user_id` is always derived from `auth.uid()`, never trusted from a request body.
- `subject_id` is resolved from an active relationship owned by the caller.
- the relationship profession matches the author’s authoritative professional type;
- the subject is at least 18 at consultation creation;
- only the author edits a draft;
- only one valid editing lease exists per consultation;
- all draft writes include the expected lease and draft revision;
- a finalized content snapshot is append-only;
- a publication points to a finalized snapshot or addendum, never a live draft;
- a client response points to one immutable publication version;
- organization membership alone never reveals consultation content;
- direct table mutation is not granted to browser roles for sensitive aggregates.

## 1. Consultation lifecycle

### States

| State | Meaning | Editable content | Permitted next states |
| --- | --- | --- | --- |
| `scheduled` | Consultation exists and may contain preparatory professional notes. | Author with lease | `in_progress`, `cancelled`, `no_show` |
| `in_progress` | Live consultation is being recorded. | Author with lease | `paused`, `finalized`, `cancelled` |
| `paused` | Work was deliberately suspended. | No; resume first | `in_progress`, `cancelled` |
| `finalized` | Canonical immutable snapshot exists. | No | `archived`, `cancelled` with reason |
| `cancelled` | Consultation will not continue. A reason is required. | No | `archived` |
| `no_show` | Scheduled client did not attend. | No | `archived` |
| `archived` | Hidden from active workflow while history is retained. | No | terminal |

Only an `in_progress` consultation can be finalized. Pausing flushes pending saves and releases the lease. Resuming requires a new lease. Reopening a finalized, cancelled, no-show or archived consultation is forbidden.

### Draft discard

Discard is an author-only destructive operation for `scheduled`, `in_progress` or `paused` records that have never been finalized or published. A never-finalized/unpublished `cancelled` draft is also discardable only through the approved ownership-only retention cleanup path. Discard is not an eighth lifecycle status.

For a normal active relationship, discard requires the current unexpired lease token, `lease_version` and expected `draft_revision`. A paused draft may acquire a lease for the sole purpose of discard; save remains forbidden until the consultation is resumed. If another device holds the lease, the author must explicitly take it over first.

The discard transaction locks the consultation and lease rows, then:

1. validates author, active entitlement, discardable state, lease token/version and current revision;
2. removes the draft aggregate and unfinalized objects queued for cleanup;
3. inserts a `consultation_discard_tombstones` row containing copied opaque IDs, timestamp and reason category, with no foreign key to the deleted aggregate;
4. never retains discarded anamnesis, measurements or attachment names in the audit log.

Ordinary `consultation_events` are content-free and append-only. Their aggregate/actor/subject identifiers are copied audit identifiers rather than cascading foreign keys, so they remain valid when a draft is discarded. The independent tombstone records the destructive outcome; neither events nor tombstones retain discarded field values, measurements or filenames.

The retention policy and whether cancelled drafts replace hard discard require approval before A.2A.

### Cancellation after finalization

A finalized consultation may be cancelled only with a reason. Cancellation does not delete or mutate its snapshot, publications, acknowledgements or addenda. The UI must explain that cancellation marks the record’s operational validity; it does not erase history.

### Initial and reassessment

`consultation_kind` is `initial` or `reassessment`.

- an initial consultation has no predecessor;
- a reassessment may reference one prior finalized consultation for the same subject;
- comparison reads immutable snapshots and never copies the prior draft;
- a new reassessment has its own author, relationship, lifecycle and publication.

### Subject abstraction and future accountless clients

`consultation_subjects` exists now to avoid making `auth.users` the lifelong consultation identifier:

- `subject_kind`: `account` or, in the future, `external`;
- `account_user_id`: unique and nullable;
- `created_by_user_id`;
- lifecycle timestamps.

A.2 permits only `account` subjects created or resolved from an active `professional_student_relationships` row. It does not permit arbitrary subject creation, name/email matching or accountless publication.

Future external-client support can attach a verified account to the stable subject without rewriting consultation IDs. Proof of control, duplicate resolution, data-subject rights, publication delivery and consent are a separate design.

### Internal reminders and attendance confirmation

An optional `scheduled_start_at` is stored as an absolute instant with an explicit IANA time zone and original local offset. The UI always displays the zone. Rescheduling creates a schedule revision and atomically cancels/rebuilds undelivered reminders. Cancellation, no-show and start invalidate undelivered reminders. Tests cover locale display and daylight-saving/offset boundaries even though the initial Brazilian zones may not currently observe DST.

At scheduling, the server creates deduplicated `consultation_reminders` for the approved lead times and `schedule_revision`. A server-side due-reminder function materializes neutral internal `user_notifications`; a production scheduler may invoke it only after separate deployment approval. Local tests call the function directly. Notification payloads contain consultation ID, schedule revision, scheduled time and safe route only.

The linked client may respond `confirmed` or `declined` through an RPC that derives client identity and requires the expected current `schedule_revision`. Each response snapshots the revision, instant, IANA zone and offset. A newer response for the same revision supersedes the current projection but does not erase response history. Rescheduling retires the prior current projection and returns the new revision to `pending`.

- is separate from publication acknowledgement;
- does not expose the consultation draft;
- does not automatically finalize, cancel or mark no-show;
- remains visible to the author through a bounded schedule DTO;
- is unavailable to organization admins and unrelated professionals.

Responses are denied after the consultation starts, is cancelled or is marked no-show; the exact pre-start cutoff requires approval. The professional remains responsible for the lifecycle transition. If the client declines, the author may reschedule or cancel. `no_show` requires a scheduled instant and is denied when database time is earlier than that instant.

The reminder notification uses neutral wording equivalent to “You have a FORJA consultation scheduled for [date/time/zone]” with “Confirm attendance” and “Decline” actions. It never describes profession-private content. Keyboard, focus, live-status and screen-reader behavior follow the same WCAG target as the editor.

### Relational fields versus snapshots

Frequently queried authority and lifecycle data remain relational:

- IDs and foreign keys;
- author, subject, relationship and profession;
- state and timestamps;
- publication and share references;
- attachment authorization;
- formula and protocol identifiers;
- raw measurement readings.

Final and published representations use canonical versioned JSON snapshots so history remains readable after field definitions evolve. JSON never replaces relational authorization.

## 3. Autosave, optimistic concurrency and editing lease

### Lease model

Use a persistent lease row, not PostgreSQL session/advisory locks. Browser requests are stateless and may use pooled connections; a session lock would not model user-visible ownership safely.

A lease contains:

- consultation ID as primary key;
- holder user ID;
- random token hash, never the raw token;
- user-chosen session/device label normalized as bounded plain text, with a neutral fallback and no passive fingerprinting;
- `lease_version`;
- acquisition, heartbeat and expiry timestamps using database time;
- takeover count.

Only the author may acquire a lease. Acquire and takeover revalidate the editable lifecycle, active relationship, profession, scope, subscription and organization context; possessing a lease is never authorization by itself. A denied attempt creates neither a lease nor a misleading takeover event. Acquire, heartbeat, takeover, save, pause and finalize are RPC operations.

### Initial interaction defaults

- autosave debounce: 1.2 seconds after the last change;
- heartbeat: every 20 seconds while the editor is active;
- lease expiry: 60 seconds after the last accepted heartbeat;
- immediate save on section change, pause and finalization request.

These are configurable application constants, not schema semantics, and require product confirmation.

### Save contract

Every save sends:

- opaque lease token;
- expected `lease_version`;
- expected `draft_revision`;
- changed field operations or a bounded section payload;
- client-generated UUID correlation ID, deduplicated within author + consultation and never used as authority.

The server:

1. locks the consultation and lease rows for the short transaction;
2. validates author, active relationship, professional type, editable status, lease token/version and current draft revision;
3. validates field definitions, size and units;
4. applies the bounded change;
5. increments `draft_revision`;
6. records a conflict event only when material, not on every keystroke;
7. returns the new revision and database save time.

A mismatch returns a conflict without overwriting data. The UI switches to read-only conflict mode and offers refresh or explicit takeover where allowed.

### Conflict recovery

Takeover changes the editor lease; it never resolves a stale `draft_revision`.

On conflict, the controller:

1. preserves unsaved operations in memory;
2. fetches the latest authorized server revision;
3. groups local operations by affected section/item;
4. shows which sections changed on the server without exposing unauthorized content;
5. requires an explicit choice to discard local operations, manually reapply them against the current revision, or send only a server-supported conflict-safe patch whose original values still match;
6. disables finalization, publication and navigation without warning until no conflict remains.

The system never auto-merges free text, measurements, calculation inputs or attachment changes. Refresh must not silently erase the in-memory operation set.

### Takeover

Another device must explicitly confirm takeover. Takeover:

- validates the same author;
- increments `lease_version`;
- invalidates the previous token;
- records an audit event;
- makes the old tab read-only on its next heartbeat/save;
- may create a content-free in-app warning.

A stale tab never silently reacquires a lease.

When a tab becomes hidden or the browser throttles timers, the UI warns that the lease may expire. A failed heartbeat changes the editor to `editing_access_expired`; the controller must explicitly reacquire or take over and then resolve any revision conflict before retrying a save.

### Relationship revocation during a draft

Revocation immediately invalidates the lease and denies edit, finalization, sharing and publication. The recommended server rule is to transition every `scheduled`, `in_progress` or `paused` consultation for that relationship to `cancelled` with the system reason `relationship_revoked`.

The author retains a bounded read-only view for the approved retention period and may use a dedicated ownership-only cleanup RPC to hard-discard that cancelled draft if the retention policy permits. This cleanup path acquires a one-purpose `cleanup` lease, locks the aggregate, requires the expected revision, and cannot change content, restart, finalize, publish or attach files. It does not require the revoked relationship to become active again. Restoring a relationship never reopens the old consultation; a new consultation is required.

This policy and retention period require approval before A.2A/A.2B.

### Offline and failure states

No sensitive consultation draft is written to `localStorage`, IndexedDB or the existing `SyncQueue` in v1. During a network failure:

- unsaved edits remain in memory for the open tab;
- a persistent `Unsaved — connection lost` status is announced visually and through `aria-live`;
- navigation and closing show a loss warning;
- finalization and publication are disabled;
- reconnect attempts use the last known revision and cannot bypass a changed lease.

## 4. Common anamnesis

The common block is a structured professional interview, not a diagnostic record. Field definitions are versioned and classify each item’s sensitivity and sharing behavior.

Initial common categories:

- consultation objective and client-stated goals;
- expectations and priorities;
- relevant self-reported health history;
- self-reported medication and supplement use;
- allergies, intolerances and relevant restrictions as reported by the client;
- injuries, pain, limitations and accessibility needs as reported;
- sleep, stress and recovery context;
- occupation, daily routine and general activity context;
- smoking/alcohol and other relevant habits with neutral wording;
- current professional follow-up;
- measurement consent/refusal and reason;
- professional observations written as observations, not diagnoses.

Every free-text field is bounded and rendered as plain text. The interface uses “reported by client” or “professional observation” labels where ambiguity could imply diagnosis.

## 5. Trainer-specific block

Private by default:

- exercise and training history;
- current program and recent training load as reported;
- training availability, environment and equipment;
- preferences, barriers and adherence context;
- movement limitations and pain flags;
- training goals and priority capacities;
- manual performance-test observations and protocol;
- session notes and next-step recommendation.

The consultation does not automatically create or overwrite a workout prescription. A later explicit action may use finalized consultation information to inform a separate versioned plan.

## 6. Nutritionist-specific block

Private by default:

- dietary history and meal routine;
- food preferences, aversions and cultural context;
- allergies/intolerances and gastrointestinal symptoms as reported;
- appetite, satiety and eating-context observations;
- hydration pattern;
- supplement use;
- food access, preparation and routine constraints;
- manual external laboratory or device information as an attachment/observation;
- session notes and next-step recommendation.

The consultation does not automatically diagnose a condition or overwrite the existing Diet module or nutrition-plan assignment. Food catalogue work and Diet behavior remain separate.

## 7. Measurements and repeated readings

### Definition registry

Each standard measurement definition is versioned and contains:

- stable key and display name;
- canonical unit and accepted input units;
- anatomical point;
- patient position;
- preparation and instruction text;
- instrument and protocol reference;
- allowed number of readings, up to three;
- reducer: mean or median;
- technical valid range and plausibility warning rules;
- eligible formulas;
- limitations and source.

The definition, unit and instruction version used are snapshotted into the consultation.

### Recording model

Each measurement records:

- measurement definition or custom label;
- protocol version;
- timestamp and operator;
- one to three raw readings with ordinal and unit;
- normalized values;
- selected reducer and calculated aggregate;
- conditions that affect comparability;
- warning code;
- professional acceptance and justification when a warned value is retained.

`observation_status` distinguishes `not_attempted`, `client_declined`, `could_not_obtain`, `instrument_limit`, `recorded` and `invalid`. Only `recorded` has readings. A refusal or unavailable measure may be finalized without an invented numeric value or warning override, but no dependent calculation is eligible. Free-text reasons remain private and bounded.

Raw readings are never overwritten by the aggregate. A correction before finalization creates a revised draft operation whose final snapshot shows the final raw set; the audit records that a correction occurred without copying sensitive values.

Custom measurements:

- use bounded plain-text name and explicit unit;
- cannot feed a curated formula automatically;
- may become formula-eligible only after a separate definition mapping is approved;
- remain comparable only when label, unit and protocol match.

### Warnings

Plausibility warnings are not diagnoses and do not block saving. They block calculation/finalization of the affected result until the author either corrects the input or provides a bounded justification. Structurally invalid values, such as a fourth reading, non-finite number or unit mismatch, are rejected.

## 8. Formula and protocol registry

### Registry contract

Every formula/protocol definition includes:

- immutable `algorithm_id` and semantic `algorithm_version`;
- family and human-readable name;
- source publication and source revision;
- required inputs and canonical units;
- eligible adult population;
- physiological reference parameters;
- exclusion rules;
- dependencies on measurement protocols or parent results;
- output unit and precision rules;
- limitations and user-facing explanation;
- recommendation priority;
- active/deprecated status.

Formula coefficients live in reviewed versioned code/data in A.2E, not in free-form database content or this design checkpoint.

Every persisted result includes:

- algorithm ID/version;
- raw input snapshot, units and measurement times;
- unrounded result and display rounding;
- explicit `equation_sex` or `reference_sex` when the source requires a binary branch;
- eligibility decision and exclusions;
- recommended or overridden selection;
- override justification;
- limitations shown at calculation time;
- parent result IDs for derived calculations.

It also stores an entity-constrained `result_kind`. Raw measurement observations alone may be `measured`; formula snapshots may be only `estimated`, `derived`, `ratio` or `population_reference` as declared by their immutable registry definition; manual BIA/device observations are `external_device_estimate`. A formula can never label its output `measured`. When a source supplies prediction error, uncertainty or validation limits, those become structured versioned metadata and client-safe explanatory text rather than an implied precision.

Gender identity remains a separate profile field and is never used implicitly as `equation_sex`. The professional must select the source-required physiological branch with an explanation of why it is requested. The selection applies only to that formula context and is included in the private calculation snapshot.

### Deterministic recommendation

The recommendation engine:

1. selects the requested calculation family;
2. filters to active versions;
3. requires complete, contemporaneous inputs and matching measurement protocol;
4. rejects source age/population exclusions;
5. withholds interpretation when only the raw calculation is eligible;
6. ranks remaining methods by approved product priority and specificity;
7. returns the recommended method, alternatives and limitations;
8. permits an eligible override only with justification;
9. never runs a deprecated version for a new result;
10. never recalculates historical results after a registry update.

If no method is eligible, the engine explains which inputs or conditions prevented calculation. It never silently substitutes another family.

### Calculation projections

Raw calculation snapshots are author-private evidence. Cross-professional sharing and client publication use separate immutable allowlisted projections.

A publishable calculation projection may contain:

- client-safe display name and `result_kind`;
- result and unit;
- algorithm ID/version and public source reference;
- measurement date;
- client-safe limitations and uncertainty text.

It unconditionally excludes:

- `equation_sex`, `reference_sex` and how they were selected;
- private raw inputs and exclusion answers;
- internal eligibility details;
- override justification;
- parent/internal row IDs and hashes;
- author-private notes.

No field flag, publication choice or professional share may override this denylist. An underlying measurement may be published only as its distinct authorized measurement item, never copied out of calculation evidence. The same rule applies to PDF manifests and professional-share projections.

Manual BIA/device observations use a separate safe projection containing only explicitly selected metric display name, value, original unit, `external_device_estimate`, measurement date and client-safe limitation text. It unconditionally excludes the physiological/device branch, device-entered settings, private measurement conditions, internal provenance/IDs/hashes and other unselected metrics.

## 9. Immutable snapshots

### Finalization transaction

Finalization:

1. validates author, active entitlement, state, current lease and expected revision;
2. validates required sections, warnings/justifications and calculation provenance;
3. orders fields and readings deterministically;
4. constructs canonical JSON with schema version;
5. computes SHA-256 over canonical UTF-8 bytes;
6. inserts `consultation_final_snapshots`;
7. sets consultation status and finalization metadata;
8. invalidates the lease;
9. writes a content-free audit event;
10. commits atomically.

Triggers or equivalent guarded functions reject changes to content rows after finalization. Lifecycle metadata may change only through explicit transition RPCs.

### Canonicalization contract

`forja.canonical-json.v1` is a versioned byte contract, not `jsonb::text`:

- input strings are normalized to Unicode NFC before snapshot construction;
- object keys are sorted recursively by Unicode code point;
- arrays use the semantic order defined by the snapshot schema;
- timestamps are UTC RFC 3339 with exactly millisecond precision and `Z`;
- measured decimals are JSON strings in plain decimal notation with the registry-defined scale, no exponent and no insignificant trailing zeros;
- non-finite numbers are forbidden;
- optional absent fields are omitted; explicit unknown values use JSON `null` only where the schema allows it;
- output is UTF-8 without BOM, whitespace or trailing newline;
- SHA-256 is computed over those exact bytes;
- the snapshot stores `canonicalization_version` beside `schema_version`.

A.2A must implement one server-side canonicalizer, publish fixed input/expected-byte/expected-hash fixtures and verify round trips. A future canonicalizer creates a new version; it never changes a historical hash.

### Calculation snapshot

Formula results are immutable evidence. A registry upgrade affects only new calculations. A reassessment may use a newer method, but comparison labels each method/version and does not imply that unlike methods are directly comparable.

### Addenda

An addendum:

- references the finalized consultation and author;
- states a bounded reason;
- contains a canonical immutable payload and hash;
- never edits the original snapshot;
- may be published only through a new publication version;
- is visibly labeled with author and creation time.

An addendum corrects or clarifies a record. New observations and measurements belong in a reassessment.

Only the original author with an active source relationship, consultation scope and current write entitlement may create an addendum to a finalized target. Under the recommended conservative rule, retention-based read after relationship revocation does not authorize a new addendum. The payload uses bounded typed corrections tied to existing snapshot item keys; it cannot smuggle a new measurement or arbitrary private block. The same visibility/publishability rules apply, and showing an addendum to the client requires a new publication version.

## 10. Shared, private and published fields

Every field definition has a server-owned `visibility_class`:

- `common`: eligible for the shared common history;
- `trainer_private`;
- `nutritionist_private`;
- `author_private`: never shared in v1.

Orthogonal server-owned flags declare whether an item is `professional_shareable` and `client_publishable`. Attachment references always use the separate attachment authorization model. A field can therefore be common and client-publishable without collapsing two different audiences into one enum.

The browser cannot change a field’s classification.

### Common history

Another professional may read finalized common items only when:

- that professional has an active relationship to the same subject;
- the relationship has `view_shared_consultation_history`;
- the exact relationship has a non-revoked current consent projection for the currently effective disclosure version;
- the item definition is in the approved common allowlist;
- the source record is finalized and not discarded;
- a bounded projection RPC omits author-private and profession-private content.

Existing relationships should default this new scope to false until the revised privacy disclosure and consent behavior are approved.

The professional cannot self-grant this scope. A client-owned authenticated RPC accepts only the exact `relationship_id`, derives `student_user_id = auth.uid()`, records the accepted disclosure version and changes only `view_shared_consultation_history`, preserving every other scope key. A client may revoke it at any time; access stops immediately. A revised disclosure requires a new explicit acceptance before that version becomes effective. Organization roles and support users cannot grant on the client’s behalf in v1.

`manage_consultations` is a separate professional capability and never implies common-history consent.

### Individual professional sharing

A finalized profession-private item may be shared to one exact recipient relationship. The grant:

- derives subject and recipient from database relationships;
- requires the recipient relationship to be active and for the same subject;
- points to an immutable snapshot item;
- never grants the whole consultation implicitly;
- records grant and revocation events;
- does not include attachments unless each attachment is shared separately.

Draft sharing is forbidden.

An attachment share uses `consultation_attachment_shares`, not a flag inside attachment metadata and not an item-share side effect. It references one immutable available attachment plus one exact active recipient relationship for the same subject. Revocation blocks new signed access but cannot retract a completed download.

Projection authorization is conjunctive: professional visibility class, writer profession, item kind, professional-shareable/client-publishable flag, actor relationship/scope and exact finalized source must all permit the operation. No single flag promotes an otherwise private value.

Revocation is evaluated on both links:

| Change | Common/private professional history | Client publication |
| --- | --- | --- |
| Recipient professional relationship revoked or org suspended | Recipient access stops immediately. | Unchanged. |
| Recipient common-history scope/consent revoked | Common access stops immediately; exact private/attachment shares also require the still-active recipient link. | Unchanged. |
| Source-author relationship revoked or source org suspended | New shares/publications stop; existing professional common/item/attachment access is suspended under the recommended privacy rule. | Existing client publications remain. |
| Exact item/attachment share revoked | New projection/signed access for that item stops. | Unchanged unless separately withdrawn. |
| Relationship reactivated | Access returns only if the consent/scope and exact grant remain active; no draft reopens. | Unchanged. |

This recommended matrix requires approval. Tests treat source and recipient relationships independently.

## 11. Client publication, acknowledgement and comment

### Publication

The client never reads the author’s consultation tables directly. The author selects publishable finalized items and attachments. The server builds a new immutable publication manifest containing only the selected, allowed content.

Each publication has:

- consultation and final snapshot IDs;
- monotonic publication version;
- exact content snapshot and schema version;
- selected attachment references;
- publisher and timestamp;
- optional superseded/revoked metadata;
- content hash.

A new publication version may supersede an older display version without erasing history. Withdrawal/revocation semantics require approval.

Before the immutable version is created, an accessible review screen shows the exact audience, selected client-safe items/calculations, attachments, exclusions and effect on the prior version. The author must explicitly confirm this preview. Unselected/private values are absent from the preview DOM, not merely visually hidden.

### Client response

The client may:

- acknowledge receipt once per publication;
- add bounded plain-text comments as separate append-only records.

Acknowledgement means receipt only. It is not agreement, informed consent, medical validation or legal electronic signature. Comments do not alter the professional record, do not become an unbounded chat thread and cannot be edited in place; a correction is a new comment.

The action label is “Confirm receipt”, never “accept”, “approve”, “agree” or “sign”. The interface states that comments are permanent additions, are not an emergency channel and do not create a live chat.

Only the responding client and original author may read acknowledgement/comment records in v1. Other linked professionals, organization roles and unrelated users are denied. Client access to their own response history persists with the publication; the author’s post-revocation view follows the approved retention policy. Notification and audit payloads never copy comment text.

## 12. Reassessment comparison

Comparison is allowed only between immutable snapshots for the same subject.

The comparison service:

- verifies the caller’s access to both snapshots;
- aligns standard measurement definition and protocol versions;
- shows raw/aggregate values, absolute delta and date;
- marks different units or methods as non-comparable unless a curated conversion exists;
- labels formula version changes;
- never compares custom measurements solely by similar text;
- supports explicit side-by-side photos only when access exists to both attachments;
- uses neutral trend language and no diagnosis.

Client comparison includes only content published to that client. Other professionals see only common or explicitly shared fields from each source.

## 13. Attachments, photos and PDF

### Storage boundary

A.2H may create one private bucket. There are no public object URLs.

Proposed path:

`consultations/{consultation_id}/{attachment_id}/{version}/{server_safe_name}`

The server reserves the exact metadata/path before upload. Client names are display metadata only and never determine authorization. No upsert or object overwrite is allowed.

Metadata records:

- author and consultation;
- optional item;
- kind: photo, source document or generated PDF;
- private bucket and exact object path;
- safe display name;
- trusted MIME after inspection, bytes and SHA-256;
- validation status: pending, quarantined, available or deleted;
- photo view/category and capture date if supplied;
- created/finalized timestamps.

Allowlisted file types, size limits, malware scanning, signed-URL lifetime and retention require approval.

### Access

- author: upload/read own draft attachments; remove only an unfinalized object through a controlled RPC;
- other professional: read only an explicitly shared available attachment for an authorized subject;
- client: read only an attachment included in their publication;
- organization admin, unrelated user and anonymous: no list/read/write/delete;
- maintenance service: quarantine and orphan cleanup only.

Short-lived signed URLs are returned after database authorization and use private/no-store delivery semantics. A revoked relationship stops new URLs immediately, but an already minted URL remains usable until its short expiry and a downloaded copy cannot be revoked.

### Photos

- private by default;
- no AI analysis in v1;
- explicit left/right or view label;
- bounded author-supplied neutral description/caption; no AI-generated alternative text;
- side-by-side comparison uses two specifically authorized immutable attachments;
- different date, posture, lighting, distance or protocol is disclosed;
- no automatic body assessment from imagery;
- view/date/protocol and comparison values remain available as adjacent text.

### PDF

The consultation PDF is a generated attachment derived from one immutable publication/report manifest. Configuration may select:

- cover and professional identity;
- published common/profession items;
- measurements and approved calculation explanations;
- selected attachments/photos;
- addenda;
- client acknowledgement status;
- neutral limitations/footer.

The PDF is not a legal signature artifact, must not expose private unselected fields and is regenerated as a new version rather than overwritten.

The A.2H foundation creates an accessibility-aware report manifest and render-job contract containing document language, logical heading/reading order, table-header semantics, selectable-text requirement, meaningful link text and author-supplied photo descriptions. It does not render a PDF binary and therefore does not claim tagged-PDF conformance. A later renderer checkpoint must generate a deterministic local artifact and inspect its tag tree before FORJA can claim an accessible PDF. The manifest stores the accessibility/schema version required from that renderer.

## 14. Audit, cancellation, archive and addenda

Audit events include:

- create, start, pause, resume, cancel, no-show and archive;
- discard tombstone;
- lease acquire, expiry and takeover;
- material autosave conflict;
- finalization;
- share/revoke;
- publication/supersession/revocation;
- acknowledgement/comment metadata;
- attachment validation and export.

Audit metadata is strictly allowlisted. It excludes field values, formula inputs/results, comments, attachment names and signed URLs. Audit rows are append-only and not directly writable by authenticated clients.

Reminder and attendance events use the same content-minimal audit rule. Internal reminder delivery never includes anamnesis, measurements, formula results or attachment metadata.

In v1, only the original author through a bounded RPC and the maintenance service may read consultation audit events. Clients, other professionals and organization roles cannot read them. The system records issuance of a shared/client projection and issuance of attachment access, but does not claim that every subsequent network read or already minted signed-URL download is audited.

Archive is a visibility/lifecycle action, not deletion. Cancellation and no-show retain reasons according to the approved retention policy. Addenda preserve correction history.

## 15. Future clients without FORJA accounts

The stable subject abstraction prepares for this future without implementing it. A separate design must decide:

- lawful identity and consent proof;
- contact verification and publication delivery;
- duplicate detection without unsafe name/email matching;
- claiming an external subject after signup;
- professional ownership when multiple professionals independently created the same person;
- data-subject access, export, correction and deletion;
- relationship conversion and tenant boundaries.

Until that design is approved, all external-subject creation and publication paths are denied.

## 16. Incremental integration with monolithic `index.html`

A.2I adds the smallest frontend seam:

- retain the current `screen-consultations` DOM island;
- add the route to trainer navigation and keep nutritionist navigation compatible;
- add a `ConsultationServiceV43` API adapter for RPC calls;
- add a `ConsultationControllerV43` for lifecycle, revision, lease and save state;
- keep normalized state under `state.consultations`;
- add a dedicated `PermissionService` presentation capability;
- render all user content with safe text nodes;
- use event delegation within the consultation screen;
- avoid touching Diet calculation, food, workout, sync or export logic;
- add focused source-contract and browser smoke tests.

Accessibility requirements:

- logical headings and landmarks;
- fully labeled inputs, units and instructions;
- fieldset/legend for related readings;
- keyboard-operable tabs, dialogs and comparison controls;
- visible focus;
- `aria-live` save/lease/conflict status without excessive announcements;
- warning text plus icon, never color alone;
- explicit error summary and focus placement;
- accessible takeover confirmation;
- reduced-motion compatibility;
- responsive layout without horizontal form overflow;
- sensitive values excluded from DOM until authorized.

Target WCAG 2.2 AA for the web flow. Verification includes a real-browser keyboard path, 200% and 400% zoom, narrow portrait reflow without two-dimensional scrolling, high-contrast/forced-colors behavior, reduced motion, error-summary links, focus restoration and throttled live announcements.

The client/consultation list has bounded keyset pagination and explicit initial loading, empty-linked-client, empty-consultation, filtered-empty, authorization-expired, error and retry states. Filters cover linked client, status and date without retaining unauthorized rows after access expires.

When a selected formula requires a physiological branch, the UI does not prefill it from gender identity. Neutral source-method language explains that the value is used only for this calculation, allows the professional/client context to decline, records source/provenance privately and withholds the calculation when no branch is supplied.

## RLS, GRANT and RPC rules

- RLS on every exposed table; force or equivalent owner-safe testing where appropriate.
- Use `(select auth.uid())` and indexes on policy predicates.
- No application authorization from `raw_user_meta_data`.
- `anon` receives no consultation table or RPC privileges.
- `authenticated` receives only the minimum read access; sensitive mutations are RPC-only.
- complex shared/client reads use bounded projection RPCs because row RLS cannot safely hide arbitrary JSON fields or columns.
- public RPCs use `security definer`, empty `search_path`, explicit caller identity and exact `authenticated` execute grant.
- internal helpers live in an unexposed schema or have execute revoked.
- security-definer code never trusts caller-provided author/client IDs.
- views, if any, use `security_invoker` or are not exposed.
- foreign keys and all RLS lookup columns are indexed.
- lease/finalization transactions are short and contain no external calls.

### Exact database access paths

| Entity group | `anon` | `authenticated` direct table DML/SELECT | Authenticated path | Maintenance |
| --- | --- | --- | --- | --- |
| subjects, consultations, items, sections | None | None | Author/list/edit RPCs only | Explicit operational role |
| measurements, readings, device observations, calculations | None | None | Author RPC; safe share/publication projection RPC | Explicit operational role |
| leases | None | None | Lease RPCs only; raw token never returned after issue | Cleanup role |
| final snapshots, addenda, discard tombstones | None | None | Author/history and safe projection RPCs | Read/retention role; no mutation |
| common consents, item/attachment shares | None | None | Client consent or author grant/revoke RPC only | Read-only investigation role |
| publications and publication attachments | None | None | Author publish RPC and client-own projection RPC | Read/retention role; no mutation |
| client/attendance responses and reminders | None | None | Exact client write RPC; client-own and original-author bounded response-history RPCs; author schedule RPC | Scheduler/retention role |
| audit events | None | None | Original-author bounded RPC only | Audit role |
| `storage.objects` | None | Policy-limited object operation only | Exact reserved path plus metadata authorization | Scanner/cleanup role |

All sensitive authenticated DML and content reads are therefore mediated by audited, bounded RPCs; RLS remains defense in depth. Exact `EXECUTE` grants are enumerated in migrations, and internal helpers are revoked.

### Immutability and referential actions

Database-level guards reject `UPDATE` and `DELETE` regardless of caller for:

- final snapshots;
- addenda;
- discard tombstones;
- publication versions and publication attachment manifests;
- client acknowledgement/comment history;
- attendance response history;
- immutable calculation evidence inside a final snapshot;
- audit events.

Mutable current projections, revocation markers and delivery status live in separate rows/events rather than rewriting immutable evidence. Tests exercise authenticated, definer-routine and maintenance test roles.

Finalized history uses `RESTRICT`/`NO ACTION` by default. Deleting an auth account, relationship, subject or consultation cannot cascade through finalized snapshots, publications, responses, addenda or audit. A future approved retention/anonymization routine must handle those identities explicitly. Draft discard cascades only through an enumerated set of unfinalized child rows; object cleanup is idempotently queued. `consultation_discard_tombstones` stores copied identifiers without a cascading consultation foreign key.

These rules align with current [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security) and [Storage access-control guidance](https://supabase.com/docs/guides/storage/security/access-control).
